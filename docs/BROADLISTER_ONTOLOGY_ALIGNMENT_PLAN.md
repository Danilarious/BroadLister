# BroadLister Ontology Alignment Plan

## Status

Bridge A is implemented as a local/static snapshot import. No runtime integration with external systems is implemented.

## Objective

Align BroadLister's media intelligence vocabulary with ProjectReckoner `ontology-core`, Tabulator, and Bucketer while preserving BroadLister as an independent local-first product.

The first implementation after approval should be advisory and read-only: BroadLister may import or load a versioned ontology/tag mapping snapshot, propose mappings in the review queue, and store accepted external references locally. It must not require ProjectReckoner, Tabulator, Bucketer, Hermes, or sevenfold to run.

## Boundary Rules

- No runtime dependency on ProjectReckoner, Tabulator, Bucketer, ontology-core, Hermes, or sevenfold.
- No direct writes into external systems.
- No autonomous outreach, Gmail, webhooks, notifications, or hidden outbound behavior.
- No client-private strategy in global tags or external artifacts.
- All imports and exports remain operator-triggered and review-gated.
- ontology-core slugs and stable IDs are references, not validators, until Bo approves a later integration phase.
- BroadLister remains the source of truth for its local journalist, outlet, article, review, campaign overlay, and export records.

## Source Systems Reviewed

BroadLister:

- `Tag`, `JournalistTag`, `OutletTag`, `ArticleTag`
- `Citation`, `ProvenanceLink`
- `ReviewItem`, `ImportBatch`
- `ClientTag`, `CampaignContact.narrative_fit_json`, `Campaign.constraints_json`, `ClientNote`

ProjectReckoner ontology-core:

- Stable IDs generated by `makeStableId(kind, payload)`
- allowed ID kinds: `entity`, `relation`, `provenance`, `event`, `claim`, `evidence`, `source`
- provenance records with actor/action/context/timestamp
- relationship types: `PARENT_OF`, `CHILD_OF`, `SYNONYM_OF`, `RELATED_TO`, `CROSSOVER`
- rule: ontology structure mutations must be reversible and not app-specific

Tabulator:

- `Link`, `Tag`, `LinkTag`, `TagRelation`
- `ExternalSourceRecord`
- `ResearchArtifact`
- `OntologyProposal`
- canonical URL and tag graph model

Bucketer:

- `Bucket`
- `Signal`
- source adapters and routing/scoring
- ontology read behavior, no ontology mutation in v1

## Concept Mapping

| BroadLister concept | ontology-core alignment | Tabulator alignment | Bucketer alignment | Scope rule |
| --- | --- | --- | --- | --- |
| `Tag` | `entity` concept reference by stable ID or slug | `Tag` mapping by normalized name/type | signal tag or bucket tag | global only when public and sourced |
| Beat | canonical concept, usually parent-level media coverage area | tag with `tag_type=system` or `user`, relation parent for topics | bucket/tag classifier | global, operator-reviewed |
| Topic | concept under or related to a beat | tag attached to links | signal tag | global when article/journalist/outlet fact is sourced |
| Outlet category | concept or controlled vocabulary entry | tag on outlet/link artifact, or metadata field | source category / feed group | global fact only |
| Journalist beat profile | claim: journalist relates to beat/topic with confidence | not a native entity; export as research artifact or link metadata | monitoring hint only | global if citation-backed |
| Article topic tags | claim: article relates to topic | `LinkTag` on canonical article URL | signal tags | global if citation-backed |
| Client relevance tags | not ontology structure; client-specific claim context | research artifact metadata only, never generic tag write-back | not a bucket classifier without review | overlay-scoped only |
| Campaign relevance | not global ontology; campaign/context claim | export artifact content only | not accepted as source classifier | campaign overlay only |
| Citation/provenance | provenance/source/evidence references | `ResearchArtifact.provenanceJson`, `Link.provenanceJson`, `ExternalSourceRecord.provenanceJson` | `raw_metadata`, source id, signal id | must travel with every artifact |
| Import batch/source artifact | provenance/source/event reference | `importBatchId`, `ExternalSourceRecord` | signal source/import run | source metadata, not fact |
| Bucketer bucket | concept group or monitoring topic | possible tag/relation context | `Bucket` | advisory input only |
| Bucketer signal | claim/evidence/source reference | link candidate or external source record | `Signal` | review-gated import |
| Tabulator link | source or article artifact | `Link` | possible signal URL | review-gated export/import |
| Tabulator metadata | provenance/context | `Link` fields and research artifact content | raw signal metadata | no client leakage |

## Mapping Granularity

BroadLister should not map every tag to ontology-core immediately. Use three tiers:

1. Canonical mappings: accepted, operator-reviewed mappings for stable beats and high-value topics.
2. Candidate mappings: deterministic suggestions from slug/name similarity, not active until approved.
3. Local-only tags: long-tail specific tags, client overlay labels, campaign narrative details, and temporary extraction labels.

## Proposed Local Mapping Shape

The Bridge A implementation uses a static JSON snapshot pasted into the UI or loaded from a local browser file. The API receives JSON text; it does not read server-side paths and does not make network calls.

Snapshot format:

```ts
interface BroadListerOntologySnapshot {
  schema: "BroadListerOntologySnapshot.v1";
  snapshot_id?: string;
  source_system: "ontology-core" | "tabulator" | "operator-curated";
  source_version: string;
  exported_at?: string;
  concepts: Array<{
    source_record_id?: string;
    concept_id?: string;
    concept_slug: string;
    label: string;
    kind: "beat" | "topic" | "format" | "region" | "language" | "broad" | "specific";
    description?: string;
    relationship_to_ontology?: "exact" | "broader" | "narrower" | "related" | "none";
    ontology_core_id?: string;
    ontology_core_slug?: string;
    tabulator_tag_id?: string;
    tabulator_normalized_name?: string;
    broadlister_tag_slug?: string;
    confidence?: "low" | "medium" | "high";
    rationale?: string;
    provenance?: Record<string, unknown>;
  }>;
}
```

Committed fixture:

- `docs/fixtures/ontology-snapshot.v1.example.json`

Preview output shows source system, source version, concept name/kind, external ID, suggested BroadLister tag slug, deterministic match if one exists, confidence, reason, mapping status, field-level changes, external IDs to add, conflict reasons, and snapshot provenance.

Preview mapping statuses:

- `create_new`: approval can create a new local `Tag` and store external references.
- `match_existing`: approval can update a deterministic local `Tag` match.
- `already_mapped`: external ID is already present locally; approval is idempotent where practical.
- `conflict`: incoming kind or external ID conflicts with an existing local tag; reject or defer for manual resolution.
- `duplicate_in_snapshot`: the same source ID appears more than once in one snapshot; reject or defer duplicates.

Future implementations may promote this to a local table if operator use proves a need. JSON is safer first because it avoids migration pressure and keeps the bridge reversible.

```ts
interface BroadListerOntologyMapping {
  id: string;
  broadlister_tag_id?: string;
  broadlister_tag_slug: string;

  ontology_core_slug?: string;
  ontology_core_kind?: "entity" | "claim" | "source" | "evidence";

  tabulator_tag_id?: string;
  tabulator_normalized_name?: string;
  mapping_state: "candidate" | "approved" | "rejected" | "retired";

  rationale: string;

```

Accepted mappings can later be copied into `Tag.external_ids_json`, but only after review:

```json

  "ontology_core_slug": "crypto-policy",

```

## Review Workflow

1. Operator imports a snapshot or local mapping file.
2. BroadLister creates `ReviewItem(kind='ontology_mapping_candidate')` records.
3. Review context shows local tag, external concept, relationship type, confidence, and source snapshot.
4. Approval creates or matches a local `Tag` by slug/name and updates only `Tag.external_ids_json`.
5. Rejection/defer does not mutate the local `Tag`.
6. No external system is called or written.

Approved external metadata uses this local JSON shape inside `Tag.external_ids_json`:

## Repeat Import And Conflict Behavior

Repeated imports of the same snapshot/source version do not create uncontrolled pending review duplicates. If a matching pending ontology review item already exists for the same `source_system`, `source_version`, and `source_record_id`, the import response reuses that review item.

Preview detects existing mappings by `Tag.external_ids_json`, by slug, and by normalized name plus kind. Approval is blocked for explicit `conflict` and `duplicate_in_snapshot` statuses. Reject/defer mutates no `Tag`.

Conflict handling remains intentionally conservative. BroadLister does not auto-merge two local tags, does not rewrite an existing external ID to a different value, and does not promote client/campaign overlay labels into global ontology mappings.

## Guardrails For Client Relevance

Client relevance and campaign relevance are not global ontology facts.

Allowed:

- Export as `BroadListerClientRelevanceArtifact`.
- Include `client_slug`, `campaign_id`, `article_id`, and cited evidence.
- Mark as overlay-scoped and operator-authored or review-approved.

Forbidden:

- Writing `trace-finance-relevant` into global `Tag` as a universal article/journalist fact.
- Exporting another client's narrative fit in a generic Tabulator link.
- Feeding campaign private strategy into Bucketer bucket definitions without explicit operator review and sanitization.

## Recommended First Bridge

Recommendation: start with `E) no bridge yet, only shared contract docs`, immediately followed by a small approved implementation of `A) read-only ontology/tag import from ProjectReckoner into BroadLister`.

Reasoning:

- The inspected ontology-core package is still early and intentionally app-agnostic.
- BroadLister needs stable mapping semantics before importing signals or exporting artifacts.
- Tabulator and Bucketer already have shapes that can accept link/signal contracts later, but mapping/client-scope mistakes would be costly.
- A read-only mapping snapshot builds confidence without runtime coupling or external writes.

Bridge A is now the active minimal implementation. Do not start `B`, `C`, or `D` until this mapping path has been used on real BroadLister tags and leakage tests prove no client overlay data can be promoted.

## Acceptance Criteria For Next Implementation

- A versioned mapping snapshot format exists in docs and fixtures. Done for `BroadListerOntologySnapshot.v1`.
- Import creates review items only. Done through `/imports/ontology`.
- Approval stores mappings locally only. Done through `Tag.external_ids_json`.
- BroadLister passes verification with ProjectReckoner, Tabulator, Bucketer, Hermes, and sevenfold stopped.
- Tests prove client relevance and campaign narrative fields cannot be emitted as global tag mappings.
- No network calls to ProjectReckoner/Tabulator/Bucketer.

## Deferred

- Live ontology-core package import.
- Tabulator API writes.
- Bucketer API reads or writes.
- Automatic tag rewriting.
- AI ontology classification.
- Multi-user sync.
- Any outreach or Gmail behavior.
